\subsection{Architecture as built}

The system still has the three parts proposed in Evaluation~1: pages that run
in the users' own browsers, a few off-chain services that we run, and smart
contracts on Ethereum Sepolia. Figure~\ref{fig:final-architecture} shows them as
they were built, following one anonymous (tier 3) election. Everything that
decides the result sits on the right. The services in the middle make the
system convenient and let voters vote without a wallet, but none of them can
change a ballot or the count, and the audit path along the bottom does not
pass through any of them.

  \centering
  \resizebox{\textwidth}{!}{\input{figures/architecture}}
  \caption{\projectname{} as built, following an anonymous election. Solid
    arrows are the numbered steps below; dotted arrows feed the indexer, a
    cache that only makes pages faster; the dashed arrow is the audit path,

    wallet sends step~5 to the election, and no relayer is involved.}

\begin{enumerate}
  \item \emph{Create.} The Election Authority's wallet calls
        \texttt{createElection} on the factory of the chosen tier. In the same
        transaction the factory deploys an EIP-1167 clone~\cite{eip1167} of
        that tier's election contract, makes the caller its authority, names
        the registrar, and fixes the counting rule, title, schedule and
        candidates.
  \item \emph{Register.} The browser creates a Semaphore
        identity~\cite{semaphore}, keeps its secret on the device and saves a
        backup file. The voter then proves an institute email address to the
        registrar by signing in with Google. The registrar checks the ID token's
        signature against Google's published keys, its issuer, audience and
        expiry, and requires its hosted-domain claim to be the institute's
        domain. The token must also carry a nonce that names this election and
        this commitment, and be at most ten minutes old, so a token that leaked
        could not register another key under the voter's email address. The registrar stores the email address against the identity's
        commitment, which is all it ever receives, and returns a receipt
        signed with EIP-712~\cite{eip712} over that commitment and this
        election. In a wallet election the voter's wallet signs a message
        tying it to the email address, and the wallet's address is what gets
        registered.
  \item \emph{Publish.} Once registration closes, the registrar does this
        on its own, without anyone asking. It sorts the commitments, builds the
        tree, pins the list to IPFS~\cite{ipfs} and calls
        \texttt{publishVoterList} with the root, the number of voters and the
        list's IPFS address. That is one transaction whatever the size of the
        list, and it freezes the list for good.
  \item \emph{Check.} The booth downloads the list by its IPFS address,
        rebuilds the tree, compares the root with the one on-chain and confirms
        that the voter's own commitment is on the list. From here on the
        registrar is not involved, so it never learns who is about to vote.
  \item \emph{Vote.} Before proving anything, the booth works out the
        nullifier its key would produce, so it can tell on loading whether this
        key has already voted. It downloads the proving files for the tree's
        depth, checks each against its pinned SHA-256 hash and builds the proof
        in a Web Worker, which keeps the page responsive. It then sends the
        choice, the nullifier and the proof to the relayer. The relayer checks
        that the election is an anonymous election from our factory, that
        voting is open, that the proof verifies, that the nullifier is unused
        and not already queued, and that the exact call succeeds in
        simulation. Only then does it sign a receipt and queue the ballot. It
        sends \texttt{castVote} to the election itself, and the booth waits
        until the nullifier appears on-chain. Any wallet can submit the same
        ballot instead.
  \item \emph{Audit.} The audit panel on every election page reads the
        election's events and state through public RPC nodes and the list
        through IPFS. In the browser, it rebuilds the root, checks every
        ballot's proof, recounts the tally and compares the winners with the
        ones the contract declared.
\end{enumerate}

The browser reads the chain through a list of public RPC nodes, falling back
from one to the next, and batches the reads it makes for each block into a
single call to a multicall contract, which runs many reads at once. The
indexer follows both factories and every election's events into a database,
waits three blocks before treating a block as settled, and rebuilds itself
from the deployment block if a block it has seen is replaced. It exists so
that lists of elections load quickly. Because anyone can create an election
through a factory, the indexer's list can be limited to elections whose
authority we recognise, and the registrar serves only elections from our
factories in which it holds the registrar role.

Table~\ref{tab:components} sets out what each part holds, and what happens if
it stops or misbehaves. The chain decides the result: if a service stops,
voting gets harder, but the result cannot change. The one exception is the
code of the pages themselves: whoever
serves them could serve a copy that leaks the voting key, so a voter trusts
the served copy just as they would trust a web wallet.

\texttt{VoterRegistry} and \texttt{TallyLib}, which Evaluation~1 drew as
separate contracts, have no address: the first is part of every election
contract and the second is compiled into it (Section~\ref{sec:divergences}).
Each factory clones exactly one implementation, which anyone can confirm by
calling its \texttt{implementation()} function, so a wallet election cannot be
passed off as an anonymous one.

Deploying code costs far more on Sepolia than under mainnet's current rules.
Deploying \texttt{MerkleElection} took 14,630,061 gas on Sepolia, about seven
times the 2,080,541 of the same deployment in our local snapshot, because
Glamsterdam~\cite{glamsterdam} brought EIP-8037, which charges 1,530 gas for
every byte of new state, including deployed code~\cite{eip8037}. Section~6
reports the effect on ordinary election steps.

The central decisions held. The voter list is still only a root on-chain, so
publishing it costs the same at any size: 147,165 gas in either tier, from 2
to 65,536 voters (Section~6). Every phase change after
configuration is still open to anyone once its time comes, so the authority
cannot stall the count. The registrar still takes no part in voting, the
relayer still runs apart from it, and the audit still reads only the chain and
IPFS. The end-to-end test on Sepolia exercises the last three: it registers
voters through the real registrar, waits for it to publish, votes through the
relayer, closes and finalizes the election and runs the in-browser audit. The
contract tests check that an account with no role can trigger every phase
change once its time has come (Section~\ref{sec:contract-tests}).
